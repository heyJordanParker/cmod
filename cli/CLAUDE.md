# Facts

- `mail.sqlite` in the cmod store holds each message between sessions until the session's cmod plugin takes it, and `openMail` in `src/serve.ts` is its one opener. It holds what no transcript holds, so a newer cmod never deletes it as it deletes an older `history-<n>.sqlite`, and a change to its shape migrates it in place under `pragma user_version`. `routeSessions` in `core/src/runtime/interfaces.ts` stores each `send` before it delivers it through the `$/act` every cmod plugin from 7.0.0 answers, marks it delivered only once that act answered, answers the sender `queued` as soon as the mail is stored, as an SMTP server answers once it queued a message, because Claude Code 2.1.329's `$.prompt.submit`, which the act runs, resolves only once the session is idle, tells a `cmod/Sessions` `Change` of `part: 'mail'` at each store and delivery, and delivers each session's mail one at a time, in id order, so a `$/hold` and a `send` never deliver one twice.
- `observe` in `src/observer.ts` is the one way the cmod program follows files, and its only `fs.watch`: a file event only hints, and each look compares every listed file's modification time and size with the last look, every `busyScanMs` for `quietAfterMs` after its start or a change and every `quietScanMs` after, because macOS drops file events under load. It marks a file the last look lacked `isNew`, and `cmod watch` counts a file gone at its settle only when it was not new, as watchman's `new` and `exists` do, because a failing build's own temporary file otherwise started the next build in a checkout that is no git repository. `cmod serve` observes a session's transcripts only while a `cmod/Sessions` `Change` listener's matcher names `part: 'messages'`, and tells a `messages` change only to such a listener, `wantsMessages` in `core/src/runtime/interfaces.ts`, because a released cmod plugin listens to its own session and to each other device's sessions with no matcher. `isStartedWithin` and a waiting `cmod program` in `src/commands/program.ts` follow the instance file with it, never `cmod/Programs`, because `cmod serve` itself starts as a service that way, as systemd's `Type=notify` reports readiness on `NOTIFY_SOCKET` and never over D-Bus. `isStartedWithin` passes no hint folder, because Bun 1.4.4 blocked the thread 0.3 to 6.4 s on a Mac to close a `fs.watch` while the suite wrote files, and up to 12.7 s to exit with one open.
- Every test file that spawns a process calls `setDefaultTimeout(spawningTestLimitMs)` from `tests/cmod.ts`, 60 s, and no test names its own limit, because Bun 1.4.4 resets the limit for each file and evaluates a shared module once per process, so a call inside `tests/cmod.ts` reaches only the first file of a `bun test` run. With every file at once on the built `cmod`, at load average 52 to 95 on a Mac, the slowest test took 26.9 s and the slowest file 59.5 s.
- Claude Code 2.1.332 hosts a `claude --bg` session in a `claude daemon` worker whose record in `<config>/sessions/<pid>.json` says `"kind": "bg"` and names its `jobId`, and `/exit` there leaves the session running, so `stopBackground` in `src/claude.ts` runs `claude stop <jobId>` for such a session and stops no other. `claude stop` kills the whole process tree of the session, so the cmod plugin's `end` asks `cmod serve` over its connection with `$/stop`, as `docker stop` goes through the daemon, and `/exit`s only a session `cmod serve` did not stop. `cmod serve` also stops a background session no cmod plugin holds yet, as right after `cmod sessions start`, and refuses `end` for any other session no plugin holds. `cmod task stop` runs the same code for an 8.10.3 cmod plugin, which ran it as a child of the session and logged the signal that killed it as a failure. `claude --bg --name <title>` writes `custom-title` and `agent-name` rows into the transcript and names the record, so `startTask` in `src/claude.ts` passes the task's title as `--name`, and the index and every list read that one title. `CMOD_TASK` in its `--settings` still carries the task, title included, for the new session's cmod plugin to record its owner's task as answered.
- `startTask` in `src/claude.ts` starts a background task with `hc run --bg --parent <terminal> --no-notify --outlive-parent` when the starting session runs in a herdr-core terminal, `terminalRunning` in `src/herdr.ts`, because herdr-core's sub-agent is a terminal with a parent and no pane, which the Herdr app and anyhost's pane list under the parent, and `claude --bg` runs the session in Claude Code's daemon, which no Herdr terminal shows. It passes `--session-id`, since only `claude --bg` prints an id, and `--no-notify`, because the task's cmod plugin mails its answer to the parent. `temporaryHome` in `tests/cmod.ts` puts a fake `hc` in each home's `bin/`, because the real one is on the Mac's `PATH`.
- The launcher, `bin/cmod`, runs a cmod it just downloaded with `CMOD_INSTALLED_VERSION` set, and `src/main.ts` then tells `cmod/Store` a `Change` of the plugins, because a newer cmod in the store has no other writer that tells, and `cmod serve` and `cmod watch` exit on that `Change` for the newer one.
