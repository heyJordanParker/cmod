# Claude Mod Manager

Claude Mod Manager (cmod) installs Claude Code mods, runs their install and uninstall steps, and builds and publishes new mods.

# Facts

- No Bun workspaces: a workspace hoists packages to the root `node_modules`, outside a plugin's import boundary.
- The release builds and tests the cmod program on Bun 1.4.4, the `bun-version` in `.github/workflows/release.yml`, so the `bun install` it runs for a mod is 1.4.4's. Bun 1.2.21's test runner hung for good when a test threw after its timeout, as a slow `cmod history follow` test does on a loaded Mac, where 1.4.4 reports it as an error between tests and finishes. Bun 1.4.4 keeps a repacked `file:` tarball of the same version in `node_modules` even with a new `--cache-dir`, so `installPackages` in `cli/src/plugin.ts` runs `bun install --force` for a mod with one. Claude Code 2.1.316 installs a plugin's packages only when the plugin ships a `bun.lock`, and runs the `bun` on the person's PATH. Bun 1.4 writes every new `bun.lock` as `lockfileVersion` 2, which Bun 1.3 and older refuse, and it left the 5.2.0 cmod plugin without its packages for anyone on an older Bun. So the release writes the cmod plugin's root `bun.lock` from scratch with `npx bun@1.2.21`. A later `bun install` on Bun 1.4 keeps an existing lock at version 1.
- `core/` publishes as `@cmodjs/core` on npm, the library mods import.
- `cli/` publishes as `@cmodjs/cli` on npm, which ships only the launcher in `cli/bin/cmod`. `cli/src/` is the cmod program's source, compiled into the binaries each GitHub release carries.
- The cmod program is the one runner of a mod's steps, and the library never runs them.
- The cmod program's `tsc` has no `claude-code` types, so each `core/src/` module it imports reaches no `claude-code` import, the `Claude` type in `core/src/runtime/claude.ts` included. That is why `readDevice` in `core/src/runtime/device.ts` takes `DeviceSources`, and `optionsOf` and `projectOptionsOf` live in `core/src/options.ts`.
- A mod's own program runs outside any session, so `cmod options` and `cmod device` give it what a session reads. `cmod options` in `cli/src/commands/options.ts` reads the person's values from `pluginConfigs["<plugin>"].options` in the user `settings.json`, and each project's `options.json` through `projectOptionsOf`, the check a session's options use too. It reads the declared options back from `plugin.json` `userConfig` with `optionsOf`, because a release install ships no `node_modules` to load the mod from. It prints no managed values, because Claude Code 2.1.317 merges them from MDM, `managed-settings.json`, a `managed-settings.d` folder, and a remote source.
- Claude Code 2.1.317 has no optional plugin dependency, and lays a provider's types file beside a mod's only for a listed dependency. So `mods.isLoaded` in `core/src/mod.ts` asks the cmod plugin's `cmod:isLoaded`, which `isLoaded` in `src/mod.ts` answers, and a mod that calls an unlisted mod types its methods in its own types file.
- The cmod program in `cli/` imports the `src/` modules of `@cmodjs/core` through the `paths` entry in `cli/tsconfig.json`, which maps `@cmodjs/core/*` to `../core/*` for `tsc`, `bun test`, and `bun build`, so it reads `core/src/` edits with no repack and each core module resolves its packages from `core/node_modules`. A `file:../core` dependency did that through per-file links on Bun 1.2.21, and Bun 1.4.4 copies the folder instead, which left core's own packages, such as `pathe`, unresolvable. The library never imports the cmod program.
- `.claude-plugin/plugin.json`, `core/package.json`, and `cli/package.json` share one version, which is the version of the cmod program too. `coreVersion` in `core/src/records.ts` holds it as well, because a published mod bundles `@cmodjs/core` and ships no `node_modules` to read it from.
- Raising that version in all three files, with the root `package.json`'s `@cmodjs/cli` and `@cmodjs/core` ranges, and pushing to `main` releases both npm packages and the cmod plugin. CONTRIBUTING.md has the release steps.
- `.github/workflows/release.yml` runs the lint, core, and cmod program suites on every push to `main`, and the cmod plugin's own suite against the committed `bun.lock`'s released core when the push releases nothing. A release runs the plugin's suite after npm serves the new core, because the plugin's ranges name it.
- The cmod program's test script starts every file in `cli/tests/` at once, because its tests wait on processes, locks, and timers far more than they compute, so the suite takes as long as its slowest file. That is why the `cmod setup` tests span several files. On a Mac whose terminal is not listed as a developer tool, each newly written script costs 150 to 330 ms on its first run, which the CI runner does not pay.
- `core/docs/` ships inside `@cmodjs/core` as the mod author docs, so a change to the Public API changes `core/docs/` in the same commit.
- The sample mods `file-tree` and `architecture-diagrams` are checked out beside this repository.
- A plugin's `cmod.call` hook answers `{ value }` or `{ deny }`. Claude Code 2.1.296 resolves the caller's `$.cmod.call` with the bare value, and rejects it with `<caller>: $.cmod.call: <deny>`. `calledAnswer` in `core/src/testing/fake-claude.ts` makes the test kit answer the same way, and `withBareRefusals` in `core/src/runtime/dependencies.ts` strips that prefix before a mod sees the error. When no hook answers, because no loaded mod's matcher selects the call or Claude Code skipped the hook that did, Claude Code 2.1.314 runs the `call` the cmod plugin adds in `engine.create`, in `hooks/register.ts`, resolves the caller with what it returns, and rejects with what it throws, bare. So that `call` throws, and a returned `{ deny }` would reach the caller as an answer. It throws `<to> did not answer in time, so Claude Code went on without it.` for a loaded mod, because the bottom also runs when Claude Code skips a mod's hook after a cancel and its 10 s budget, and `notInstalled(to)` for any other. `isLoaded` in `src/mod.ts` counts a mod as loaded when it is among the plugin versions this Claude Code process loaded, or when it told the cmod plugin its parts in this process, which `servePages`' `declared` holds, because a `--plugin-dir` mod is never in `installed_plugins.json`. A mod that left the loaded versions at a reload counts as not loaded again, even after it told its parts.
- Every failure cmod catches for a mod goes through `fail` on the toaster from `createToaster` in `core/src/runtime/toaster.ts`, which sends it with `cmod.call` method `cmod:failed` to the cmod plugin. `failureLog` in `src/settings.ts` answers it: it keeps the Log, one file per session at `log/<session>.json` in the cmod plugin's data folder, so sessions never write the same file, and the Settings Log reads the newest 100 across every file. It answers `{ showsToast: true }` for a critical failure (`isCritical` on `Failure`), a mod run from its checkout (`marketplaceOf(root, mod)` is undefined, so a `cmod link` or `--plugin-dir` checkout counts as the author's), or `showsInstalledModErrors` in `preferences.json`. A refused call, or an answer that is not `{ showsToast: true or false }`, shows the toast whatever the failure, as with a cmod before 4.3.0, so the test kit, whose cmod refuses the method, shows every failure. A trouble cmod works around, which used to go only to Claude Code's debug log, goes through `claude.ui.warn(id, text)`, which `createLifecycle` binds to the toaster's `warn`: it writes the debug line and sends `cmod:failed` with `level: 'warning'`, and never shows a toast. Each failure sends its mod's `version` and `core`, and `failureLog` adds the session, the cmod plugin's version, the cmod program's, and Claude Code's from `$.session.version()`, and counts each repeat of a mod and id with `count` and `firstAt`, so the Log says which versions a failure still happens on. `mod.log` stays a debug line, because it is the author's own log. The toast stays, with Copy and Report. `fail` waits one `clock.after(0)` before the call, because Claude Code skips the cmod plugin's `cmod.call` hook during the cmod plugin's own call to the mod, such as a draw or a press, and the cmod plugin's call to itself waits in `holdUntilStarted` until its setup returned its API. Settings writes `preferences.json`, then `store-changed`.
- Claude Code runs `session.start` down the chain of plugins, and `startMod` in `core/src/register.ts` starts its mod while it passes `session.start` on, so every mod starts at once, whatever its place in the chain. A `cmod.call` to a mod that is still starting waits for its start, and one to a mod waiting on its install is refused with "is installing". The exception is a mod's `cmod:subscribe` and `cmod:watchBefore` to the cmod plugin while it installs: its lifecycle keeps the latest of each per mod and session, answers `null`, and runs them once it is active, because a mod sends them only when its listeners change, so a refused one left the mod deaf for the session.
- `sessions` and `settings.<source>.update` reach the cmod plugin through `cmod.call`, and it answers by running `cmod history` and `cmod settings`. The conversation index is `history-12.sqlite` in the cmod store. It holds where each message is in its transcript, never a copy, plus each session's turns with the device each ran on, contexts, and tasks, and a change to what it holds or how it reads a transcript raises the number in the file's name, so a newer cmod deletes the older file instead of migrating it.
- The cmod plugin is the one reader of the running conversation: `registerMod` adds `session.append`, `session.receive`, `agent.spawn`, and `prompt.attachment` handlers only for it, and the cmod plugin's own `session.compact` route reads each compaction, added ahead of the `before` routes so it also records a compaction that a mod's `beforeContextEnd` `summary` answers without Claude Code's model, `core/src/session/conversation.ts` turns each row into messages, turns, contexts, and tasks, and the plugin pushes each change to the mods that listen through `cmod.call`. Other running sessions reach it through one `cmod history follow` child, woken by `fs.watch`. It indexes at session start only while a mod other than cmod is set up.
- Claude Code's transcript rows name no computer, so the cmod plugin's `beforeSessionStart` note in `src/mod.ts` names the device at every startup, resume, clear, and compact, as the sentence `deviceNote` in `core/src/session/context/turn/device.ts` writes. The sentence starts with the time, because Claude Code 2.1.314 drops a resume's SessionStart note that repeats any earlier note of the conversation, so a session that went back to a computer it ran on before kept the other computer's device. `createConversation` gives each main turn the device of the last such sentence in the main transcript before it, and each task's turns the device its session had when the task started, because the index reads a session's whole main transcript before its task transcripts, so a sentence a subagent's compaction left in a task transcript would have moved the main turns read after it. Transcripts keep that sentence forever, so its wording never changes. Claude Code 2.1.308's `$` has no computer facts and its hooks `crypto.subtle` has only `digest` (`.claude-plugin/types/claude-code/index.d.ts`), so `readDevice` in `core/src/runtime/device.ts` runs `uname`, `ioreg`, and `scutil`, or reads `/etc/machine-id` and then `/var/lib/dbus/machine-id`, as systemd and D-Bus do, and builds the HMAC-SHA256 of systemd's `sd_id128_get_machine_app_specific` from `digest`. Many Debian and Node devcontainers hold neither file or an empty one, so `readDevice` rejects with `MissingMachineId`, and the cmod plugin leaves that start's note without a device and logs one debug line instead of a failure the person cannot fix.
- The cmod plugin owns every `before` point of its session, in `core/src/runtime/before.ts`, because only it hears `session.append`, `session.receive`, `agent.spawn`, and `prompt.attachment`, and only its `session.compact` route reads each compaction. It asks a mod of its own session by `cmod.call` and a mod of another session over the relay. `testMod` installs the same points in front of the tested mod, and the cmod plugin's `servePages` beneath it for `command.run` and a pane's `ui.press`, so an asked page request opens only in the person's frame, as in a live chain where cmod comes last.
- Every `Session` action and every `before` on another running session travels as a `<cmod-relay>` message the cmod plugin sends with `$.session.send` and the other session's cmod plugin consumes in `session.receive`, in `core/src/runtime/conversations.ts`. A mod's `before` registrations are a file per session under the cmod plugin's data folder, `before/<session>.json`, which each cmod plugin reads at its start and on a relayed `watch`, and its `on` subscriptions are `listeners/<session>.json`. A mod sends them only when its listeners change, and Claude Code 2.1.301's `/reload-plugins` restarts only the plugins whose code changed, so a cmod plugin that restarts alone reads its own session's two files back.
- Claude Code's `TaskCreate`, `TaskUpdate`, and `TaskList` tools and its `TaskCreated` and `TaskCompleted` hooks are its todo checklist. A cmod `Task` is work handed to another session, whose `owner` is that session, and Claude Code's checklist is not part of the model. - A mod's `rules/` folder reaches Claude Code as a symbolic link in Claude Code's rules folder, which `syncRules` in `cli/src/rules.ts` places and removes from the settings files. cmod records each link it places, and each `claudeMdExcludes` entry it adds to keep a user-wide mod's rules out of a project that turned the mod off, in `rules.json` in the cmod store, and undoes only those, so a link or setting a person made is never touched. Claude Code 2.1.296 loads a linked subfolder, a rule without `paths` only at a session's start, and a rule with `paths` at the first matching read, so the cmod plugin adds a rule without `paths` to a running session as a note.
