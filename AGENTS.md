# Claude Mod Manager

Claude Mod Manager (cmod) installs Claude Code mods, runs their install and uninstall steps, and builds and publishes new mods.

# Facts

- The Architect chose VS Code's extension architecture as the precedent for cmod's whole extension system, with a Claude Code session where VS Code has a window, so a new part of cmod is judged against VS Code first. A mod is an extension, the session's hooks worker its extension host, a `singleInstance` or `isService` program a language server, `cmod serve` the shared process, which holds every program's providers, and `provide` from `mod.js` `registerXProvider`. How cmod is built in `core/docs/index.md` maps every part, and why a part departs from VS Code.
- No Bun workspaces: a workspace hoists packages to the root `node_modules`, outside a plugin's import boundary.
- The release builds and tests the cmod program on Bun 1.4.4, the `bun-version` in `.github/workflows/release.yml` and `test.yml`, so the `bun install` it runs for a mod is 1.4.4's. Bun 1.2.21's test runner hung for good when a test threw after its timeout, as a slow `cmod sessions follow` test does on a loaded Mac, where 1.4.4 reports it as an error between tests and finishes. Bun 1.4.4 keeps a repacked `file:` tarball of the same version in `node_modules` even with a new `--cache-dir`, so `installPackages` in `cli/src/plugin.ts` runs `bun install --force` for a mod with one.
- `types/` holds what Claude Code 2.1.329 writes into a plugin's `.claude-plugin/types/`, all but its `.gitignore`: `tsconfig.json`, `claude-code/`, `claude-code-tools/`, and `claude-code-mcp/`, which git tracks so a push installs no Claude Code to test. No npm package ships them: Claude Code writes them only into a plugin it loads. The build and the type checks of `core/` and the cmod plugin read `claude-code/` and `claude-code-tools/`, and `typeCheck` in `cli/tests/new.test.ts` copies all four into a new mod's `.claude-plugin/types/`, the folder the mod's `tsconfig.json` extends. `types/write-claude-code.sh <version>` writes them from a given version, and `.github/workflows/claude-code.yml` runs it daily with `latest` and then every Linux suite. The root `package.json` `"files"` lists `types/index.d.ts` alone, so the cmod plugin's release ships only its own types, the file its `plugin.json` `"types"` names.
- `core/` publishes as `@cmodjs/core` on npm, the library mods import.
- `cli/` publishes as `@cmodjs/cli` on npm, which ships only the launcher in `cli/bin/cmod`. `cli/src/` is the cmod program's source, compiled into the binaries each GitHub release carries. `cli/src/main.ts` imports each command only when it runs, and the build compiles to bytecode, because a session starts cmod for every `cmod.call` it answers with the program: each cut the CPU `cmod --version` takes on a Mac by half or more.
- Claude Code 2.1.316 installs a plugin's packages only when the plugin ships a `bun.lock`, and only with a `bun` on the person's PATH, which a new Linux machine lacks. So the cmod plugin's release ships no `bun.lock`: its root `package.json` `"files"` lists `cli/bin/cmod` and `cli/package.json`, which `cmod publish` releases because `"files"` names them, and `setup/bootstrap.sh` runs that launcher. Its hooks module bundles `@cmodjs/core`, from the core the release workflow just built, unpacked over the root `node_modules`, so the release waits on no npm publish, and the root `bun.lock` is the checkout's alone.
- The cmod program is the one runner of a mod's steps, and the library never runs them.
- `cmod setup <folder>` sets up the copy Claude Code installed, the `cmod link` checkout or the enabled copy `listPlugins` names, whatever folder its caller gives, `installedCopy` in `cli/src/commands/setup.ts`, and the given folder only when Claude Code lists no copy but a `--plugin-dir` one, as Homebrew and dpkg keep one record of what is installed that only the installer changes. Claude Code keeps a session on the copy it loaded and every old copy on disk, and each start of a mod and each prompt after it runs `cmod setup` with the session's own folder whenever that copy differs from the record, so an old session set a mod back to its old version, whose service broke the newer database. Every session runs the newest cmod program, so the rule reaches every released core. A `--plugin-dir` session over an installed copy runs on the installed program, and `cmod link` makes a checkout the computer's version. The record's `installedBy` names the session, from `CLAUDE_CODE_SESSION_ID`, and the process that asked for the setup. A setup counts a copy as current only when the record names its folder, so a copy at the same version as the recorded one still takes the record over. The record moves to another copy and is never torn down while one is left: `cmod unlink` and `cmod remove` of one copy set up the copy `installedCopyOf` names, and run `teardownInTerminal`, which deletes the mod's data folder and secrets, only when Claude Code lists no copy, as the cmod plugin's `watchRemovals` in `src/mod.ts` tears down only a name `enabledPlugins` no longer holds. Services follow the same rule: `isInstalledCopy` in `core/src/runtime/lifecycle.ts` reads, once the session's own setup settled, whether the record names the session's copy, always for cmod, and only then does `removeUndeclaredServices` remove a service or the `program` job's `isService` write one, while another copy follows it as a `singleInstance` one. A released core writes services from an old copy until its session reloads, as it passes `cmod program` no folder.
- A linked checkout's program build is `bin/<program>/<version>/<program>.linked` in the cmod store, `linkedProgramPath` in `core/src/records.ts`, beside the released download at `programPath`, so `cmod link` and `cmod unlink` switch the copy that runs by moving the `programs/<program>` link, with no download, as `programOf` in `cli/src/program.ts` picks: the build for a linked checkout, and for any other copy its release, or the build when it has no release, as for a `cmod try` folder. A setup counts as current only while `programs/<program>` points at the file `programOf` picks, and `programModifiedMs` takes the newer of the two files, so a rebuild of either reruns the install step with the new program. `readCmodVersion` counts a version whose only cmod is a linked build, because a linked cmod checkout ahead of the last release is the computer's cmod.
- The cmod program's `tsc` reads the `claude-code` and `claude-code-tools` types from `types/`, through `typeRoots` and `types` in `cli/tsconfig.json`, because `connectScript` in `cli/src/script.ts`, for `cmod run`, `sessions`, and `terminal`, runs `serveConversations` and `createSessionsClient`, which take the `Claude` type. So `mods.isLoaded` in `core/src/mod.ts` asks the cmod plugin's `cmod:isLoaded`, which `isLoaded` in `src/mod.ts` answers, and a mod that calls an unlisted mod types its methods in its own types file.
- The cmod program in `cli/` imports the `src/` modules of `@cmodjs/core` through the `paths` entry in `cli/tsconfig.json`, which maps `@cmodjs/core/*` to `../core/*` for `tsc`, `bun test`, and `bun build`, so it reads `core/src/` edits with no repack and each core module resolves its packages from `core/node_modules`.
