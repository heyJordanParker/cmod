# Claude Mod Manager

Claude Mod Manager (cmod) installs Claude Code mods, runs their install and uninstall steps, and builds and publishes new mods.

# Facts

- No Bun workspaces: a workspace hoists packages to the root `node_modules`, outside a plugin's import boundary.
- The release builds and tests the cmod program on Bun 1.4.4, the `bun-version` in `.github/workflows/release.yml` and `test.yml`, so the `bun install` it runs for a mod is 1.4.4's. Bun 1.2.21's test runner hung for good when a test threw after its timeout, as a slow `cmod history follow` test does on a loaded Mac, where 1.4.4 reports it as an error between tests and finishes. Bun 1.4.4 keeps a repacked `file:` tarball of the same version in `node_modules` even with a new `--cache-dir`, so `installPackages` in `cli/src/plugin.ts` runs `bun install --force` for a mod with one.
- `types/` holds what Claude Code 2.1.318 writes into a plugin's `.claude-plugin/types/`, all but its `.gitignore`: `tsconfig.json`, `claude-code/`, `claude-code-tools/`, and `claude-code-mcp/`, which git tracks so a push installs no Claude Code to test. No npm package ships them: Claude Code writes them only into a plugin it loads. The build and the type checks of `core/` and the cmod plugin read `claude-code/` and `claude-code-tools/`, and `typeCheck` in `cli/tests/new.test.ts` copies all four into a new mod's `.claude-plugin/types/`, the folder the mod's `tsconfig.json` extends. `types/write-claude-code.sh <version>` writes them from a given version, and `.github/workflows/claude-code.yml` runs it daily with `latest` and then every Linux suite. The root `package.json` `"files"` lists `types/index.d.ts` alone, so the cmod plugin's release ships only its own types, the file its `plugin.json` `"types"` names.
- `core/` publishes as `@cmodjs/core` on npm, the library mods import.
- `cli/` publishes as `@cmodjs/cli` on npm, which ships only the launcher in `cli/bin/cmod`. `cli/src/` is the cmod program's source, compiled into the binaries each GitHub release carries. `cli/src/main.ts` imports each command only when it runs, and the build compiles to bytecode, because a session starts cmod for every `cmod.call` it answers with the program: on this Mac `cmod --version` took 71M CPU cycles compiled and 35M after, and 163M from source and 61M after.
- Claude Code 2.1.316 installs a plugin's packages only when the plugin ships a `bun.lock`, and only with a `bun` on the person's PATH, which a new Linux machine lacks. So the cmod plugin's release ships no `bun.lock`: its root `package.json` `"files"` lists `cli/bin/cmod` and `cli/package.json`, which `cmod publish` releases because `"files"` names them, and `setup/bootstrap.sh` runs that launcher. Its hooks module bundles `@cmodjs/core`, from the core the release workflow just built, unpacked over the root `node_modules`, so the release waits on no npm publish, and the root `bun.lock` is the checkout's alone.
- The cmod program is the one runner of a mod's steps, and the library never runs them.
- The cmod program's `tsc` has no `claude-code` types, so each `core/src/` module it imports reaches no `claude-code` import, the `Claude` type in `core/src/runtime/claude.ts` included. That is why `readDevice` in `core/src/runtime/device.ts` takes `DeviceSources`, and `optionsOf` and `projectOptionsOf` live in `core/src/options.ts`.
- A mod's own program runs outside any session, so `cmod options` and `cmod device` give it what a session reads. `cmod options` in `cli/src/commands/options.ts` reads the person's values from `pluginConfigs["<plugin>"].options` in the user `settings.json`, and each project's `options.json` through `projectOptionsOf`, the check a session's options use too. It reads the declared options back from `plugin.json` `userConfig` with `optionsOf`, because a release install ships no `node_modules` to load the mod from. It prints no managed values, because Claude Code 2.1.317 merges them from MDM, `managed-settings.json`, a `managed-settings.d` folder, and a remote source.
- Claude Code 2.1.317 has no optional plugin dependency, and lays a provider's types file beside a mod's only for a listed dependency. So `mods.isLoaded` in `core/src/mod.ts` asks the cmod plugin's `cmod:isLoaded`, which `isLoaded` in `src/mod.ts` answers, and a mod that calls an unlisted mod types its methods in its own types file.
- The cmod program in `cli/` imports the `src/` modules of `@cmodjs/core` through the `paths` entry in `cli/tsconfig.json`, which maps `@cmodjs/core/*` to `../core/*` for `tsc`, `bun test`, and `bun build`, so it reads `core/src/` edits with no repack and each core module resolves its packages from `core/node_modules`. A `file:../core` dependency did that through per-file links on Bun 1.2.21, and Bun 1.4.4 copies the folder instead, which left core's own packages, such as `pathe`, unresolvable. The library never imports the cmod program.
- `.claude-plugin/plugin.json`, `core/package.json`, and `cli/package.json` share one version, which is the version of the cmod program too. `coreVersion` in `core/src/records.ts` holds it as well, because a published mod bundles `@cmodjs/core` and ships no `node_modules` to read it from.
- Raising that version in all three files and pushing to `main` releases both npm packages and the cmod plugin. CONTRIBUTING.md has the release steps.
- `.github/workflows/release.yml` runs every suite on every push to `main`, the cmod plugin's own suite on the core that push built. Its `version` job, which asks npm and the remote what the version still needs beside the tests, its `test` job, which runs the Linux suites from `.github/workflows/test.yml`, and its `release` job run on `ubuntu-latest`, and its `macos` job runs only the test files that reach code macOS alone runs: `secret.test.ts`, `try.test.ts`, `install.test.ts`, `launcher.test.ts`, and `program.test.ts`, whose service tests reach launchd, in `cli/tests/`, and `register.test.ts` in `core/tests/`. A probe on 2026-11-03 waited 3 s for a Linux runner and 5 minutes for a macOS one, GitHub dropped two macOS jobs that day as `not acquired by Runner of type hosted`, and the cmod program's suite took 43 s on Linux and 83 s on macOS. Bun cross-compiles the four `cmod-<os>-<arch>` builds on Linux, and a `darwin-arm64` build made there carries an ad-hoc signature and runs on a Mac. Linux's `sh -c` keeps its shell between cmod and a mod's step, where macOS's runs the step in its place, so a test step reaches cmod through `cmodOfStep` in `cli/tests/cmod.ts`, never `$PPID`.
- The cmod program's test script starts every file in `cli/tests/` at once, because its tests wait on processes, locks, and timers far more than they compute, so the suite takes as long as its slowest file. That is why the `cmod setup` tests span several files, and why `watch.test.ts`, `lock.test.ts`, `program.test.ts`, and `history.test.ts` declare each test that shares nothing with `test.concurrent`: each test waits seconds on cmod's own timers or processes in its own home, so one after another they took 43, 28, 26, and 23 seconds, and together each file takes as long as its slowest test. On the 4-core Linux runner the suite keeps about three cores busy, so a file whose tests already end before the slowest file gains nothing at once: `cancel.test.ts` at once ended at 12 s instead of 20 s, and the suite ended at 24 to 25 s instead of 19 s. `new.test.ts` runs `cmod new` once and reads that mod, or a copy of it for a test that changes it, because each `cmod new` installs packages. On a Mac whose terminal is not listed as a developer tool, each newly written script costs 150 to 330 ms on its first run, which the CI runner does not pay.
- `core/docs/` ships inside `@cmodjs/core` as the mod author docs, so a change to the Public API changes `core/docs/` in the same commit.
- The sample mods `file-tree` and `architecture-diagrams` are checked out beside this repository.

Claude Code 2.1.296 resolves the caller's `$.cmod.call` with the bare value, and rejects it with `<caller>: $.cmod.call: <deny>`. `calledAnswer` in `core/src/testing/fake-claude.ts` makes the test kit answer the same way, and `withBareRefusals` in `core/src/runtime/dependencies.ts` strips that prefix before a mod sees the error. So that `call` throws, and a returned `{ deny }` would reach the caller as an answer.
