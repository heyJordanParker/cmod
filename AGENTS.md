# Claude Mod Manager

Claude Mod Manager (cmod) installs Claude Code mods, runs their install and uninstall steps, and builds and publishes new mods.

# Facts

- No Bun workspaces: a workspace hoists packages to the root `node_modules`, outside a plugin's import boundary.
- `core/` publishes as `@cmodjs/core` on npm, the library mods import.
- `cli/` publishes as `@cmodjs/cli` on npm, which ships only the launcher in `cli/bin/cmod`. `cli/src/` is the cmod program's source, compiled into the binaries each GitHub release carries.
- The cmod program is the one runner of a mod's steps, and the library never runs them.
- The cmod program in `cli/` imports the `src/` modules of `@cmodjs/core` as a dev dependency. The library never imports the cmod program.
- `.claude-plugin/plugin.json`, `core/package.json`, and `cli/package.json` share one version, which is the version of the cmod program too. `coreVersion` in `core/src/records.ts` holds it as well, because a published mod bundles `@cmodjs/core` and ships no `node_modules` to read it from.
- Raising that version in all three files, with the root `package.json`'s `@cmodjs/cli` and `@cmodjs/core` ranges, and pushing to `main` releases both npm packages and the cmod plugin. CONTRIBUTING.md has the release steps.
- `core/docs/` ships inside `@cmodjs/core` as the mod author docs, so a change to the Public API changes `core/docs/` in the same commit.
- The sample mods `file-tree` and `architecture-diagrams` are checked out beside this repository.
- A plugin's `cmod.call` hook answers `{ value }` or `{ deny }`. Claude Code 2.1.296 resolves the caller's `$.cmod.call` with the bare value, and rejects it with `<caller>: $.cmod.call: <deny>`. `calledAnswer` in `core/src/testing/fake-claude.ts` makes the test kit answer the same way, and `withBareRefusals` in `core/src/runtime/dependencies.ts` strips that prefix before a mod sees the error.
- Every failure cmod catches for a mod goes through `fail` on the toaster from `createToaster` in `core/src/runtime/toaster.ts`, which sends it with `cmod.call` method `cmod:failed` to the cmod plugin. `failureLog` in `src/settings.ts` answers it: it keeps the Log, one file per session at `log/<session>.json` in the cmod plugin's data folder, so sessions never write the same file, and the Settings Log reads the newest 100 across every file. It answers `{ showsToast: true }` for a critical failure (`isCritical` on `Failure`), a mod run from its checkout (`marketplaceOf(root, mod)` is undefined, so a `cmod link` or `--plugin-dir` checkout counts as the author's), or `showsInstalledModErrors` in `preferences.json`. A refused call, or an answer that is not `{ showsToast: true or false }`, shows the toast whatever the failure, as with a cmod before 4.3.0, so the test kit, whose cmod refuses the method, shows every failure. The toast stays, with Copy and Report. `fail` waits one `clock.after(0)` before the call, because Claude Code skips the cmod plugin's `cmod.call` hook during the cmod plugin's own call to the mod, such as a draw or a press, and the cmod plugin's call to itself waits in `holdUntilStarted` until its setup returned its API. Settings writes `preferences.json`, then `store-changed`.
- Claude Code runs `session.start` down the chain of plugins, and `startMod` in `core/src/register.ts` starts its mod while it passes `session.start` on, so every mod starts at once, whatever its place in the chain. A `cmod.call` to a mod that is still starting waits for its start, and one to a mod waiting on its install is refused with "is installing". The exception is a mod's `cmod:subscribe` and `cmod:watchBefore` to the cmod plugin while it installs: its lifecycle keeps the latest of each per mod and session, answers `null`, and runs them once it is active, because a mod sends them only when its listeners change, so a refused one left the mod deaf for the session.
- `sessions` and `settings.<source>.update` reach the cmod plugin through `cmod.call`, and it answers by running `cmod history` and `cmod settings`. The conversation index is `history-11.sqlite` in the cmod store. It holds where each message is in its transcript, never a copy, plus each session's turns, contexts, and tasks, and a change to what it holds or how it reads a transcript raises the number in the file's name, so a newer cmod deletes the older file instead of migrating it.
- The cmod plugin is the one reader of the running conversation: `registerMod` adds `session.append`, `session.receive`, `agent.spawn`, and `prompt.attachment` handlers only for it, and the cmod plugin's own `session.compact` route reads each compaction, added ahead of the `before` routes so it also records a compaction that a mod's `beforeContextEnd` `summary` answers without Claude Code's model, `core/src/session/conversation.ts` turns each row into messages, turns, contexts, and tasks, and the plugin pushes each change to the mods that listen through `cmod.call`. Other running sessions reach it through one `cmod history follow` child, woken by `fs.watch`. It indexes at session start only while a mod other than cmod is set up.
- The cmod plugin owns every `before` point of its session, in `core/src/runtime/before.ts`, because only it hears `session.append`, `session.receive`, `agent.spawn`, and `prompt.attachment`, and only its `session.compact` route reads each compaction. It asks a mod of its own session by `cmod.call` and a mod of another session over the relay. `testMod` installs the same points in front of the tested mod, and the cmod plugin's `servePages` beneath it for `command.run` and a pane's `ui.press`, so an asked page request opens only in the person's frame, as in a live chain where cmod comes last.
- Every `Session` action and every `before` on another running session travels as a `<cmod-relay>` message the cmod plugin sends with `$.session.send` and the other session's cmod plugin consumes in `session.receive`, in `core/src/runtime/conversations.ts`. A mod's `before` registrations are a file per session under the cmod plugin's data folder, `before/<session>.json`, which each cmod plugin reads at its start and on a relayed `watch`, and its `on` subscriptions are `listeners/<session>.json`. A mod sends them only when its listeners change, and Claude Code 2.1.301's `/reload-plugins` restarts only the plugins whose code changed, so a cmod plugin that restarts alone reads its own session's two files back.
- Claude Code's `TaskCreate`, `TaskUpdate`, and `TaskList` tools and its `TaskCreated` and `TaskCompleted` hooks are its todo checklist. A cmod `Task` is work handed to another session, whose `owner` is that session, and Claude Code's checklist is not part of the model. A mod hears the two hooks as `sessions.current.onTodoCreate` and `onTodoComplete`, with a `before` method for each.
- A mod's `rules/` folder reaches Claude Code as a symbolic link in Claude Code's rules folder, which `syncRules` in `cli/src/rules.ts` places and removes from the settings files. cmod records each link it places, and each `claudeMdExcludes` entry it adds to keep a user-wide mod's rules out of a project that turned the mod off, in `rules.json` in the cmod store, and undoes only those, so a link or setting a person made is never touched. Claude Code 2.1.296 loads a linked subfolder, a rule without `paths` only at a session's start, and a rule with `paths` at the first matching read, so the cmod plugin adds a rule without `paths` to a running session as a note.
- Claude Code refuses a hooks module whose `addHook` event name is not a string literal at the call site, so `registerMod` in `core/src/register.ts` names each event literally, and a test in `core/tests/register.test.ts` checks it does and that every hook a session method hears is registered. Claude Code 2.1.309 throws `on() is for register(); a hook may not register hooks` for an `addHook` after `register` returned, and sends each registered event to the plugin's worker whether or not a route listens, so every mod registers at load each event it could hear, 42 for a mod and 48 for the cmod plugin. Claude Code 2.1.310 hops to the hooks worker only when some plugin's registration selects the event, one without a matcher or with a matcher that matches, and then runs the chain from the first plugin that selects it, so a matcher saves the hop only when every plugin's matcher passes the event by. That rule comes from reading the 2.1.310 binary: on 2.1.309 a live session still logged one `command.describe` hop per command with the cmod plugin's `{ command: /--/ }` matcher, while its route ran only for the hotkey commands. So each mod's `cmod.call` matches `{ to: <its name> }`, and a call runs only the hook of the mod it names.

- Every note a mod gives travels inside its tag, `<{mod}_mod>…</{mod}_mod>`, from `modNote` in `core/src/session/context/turn/message/note.ts`, and `unplacedOf` in `message.ts` turns each tagged block of a `hook_additional_context` row, or a user message that holds only tagged blocks, into a `Note` from that mod. So every hook `registerMod` adds after `session.start` carries one, `lifecycle.caught` in `core/src/runtime/lifecycle.ts`, which answers with the failure answer a route gave `router.add` beside its hook, so each gate refuses in its own answer's shape.
- Every `Mod` member is the mod's own. What is Claude Code's or the computer's is an import from `mod.js`: `sessions`, `settings`, `model`, `fs`, `metadata`, `process`, and `http`, each bound to the mod that runs it. A 4.x bundle still checks its own grants in `consent.json` in the cmod store, so `cmod setup` approves the consent hash and every item a 4.x mod declares, without asking.
- Every newer cmod runs every mod built on `@cmodjs/core` 4.0.0 or later, so a mod's `cmod` dependency is `>=` the `oldestCmodVersion` of the `@cmodjs/core` it bundles, from `core/src/records.ts`, which `cmod check` writes and `cmod publish` requires. `oldestCmodVersion` is the oldest cmod the library runs on, raised only when the library starts using something an older cmod lacks, and a 4.x core, which lacks it, counts at its own version. So the `--events` lines, the `cmod.call` methods in both directions, the relay kinds and actions, `widgets.json`, and the consent hash keep their 4.0.0 shape: a newer cmod adds a line type, a method, a kind, an action, or a field, and never changes or removes one. `core/tests/contract.test.ts` freezes the event lines, the consent hash, and the methods a mod answers, the contract test in `tests/mod.test.ts` the methods the cmod plugin answers, and `core/tests/runtime/conversations.test.ts` and `core/tests/runtime/widgets.test.tsx` the relay kinds and `widgets.json`. A relay receiver refuses a kind or action it lacks by name, and the `widgets.json` writer keeps the areas, row fields, and placed widgets it does not know.
- Claude Code 2.1.305 loads one plugin named `cmod` when several marketplaces list one, the first source whatever its version, and checks each mod's range only against its own marketplace's copy. So the cmod plugin runs `cmod list --json` at its start, and whenever the modification time of Claude Code's `installed_plugins.json` or of the cmod store's `plugins-changed` differs from the pair in `pluginsCheckedAt`, because a linked checkout's `plugin.json` edit changes only `plugins-changed`. It runs `cmod update <name>` once per mod set and plugin versions, which `cmod:cmod-updated-for` holds, for cmod when the list shows a mod off for an older cmod, and for any plugin with two copies at different versions, because a mod's dependency on another mod is listed in its marketplace the same way. A mod whose cmod program stays older than its `oldestCmodVersion` for a minute runs `cmod update cmod` too.
- The library runs the cmod program only as `<store>/programs/cmod`, never a `cmod` on PATH, and reads its version from the newest folder of `<store>/bin/cmod`, the one the launcher runs, without starting it.
- A `program` job with `singleInstance` runs one copy per computer, and the election lives in the cmod program, because Claude Code 2.1.309's `$.fs` has only `read`, `write`, `list`, `exists`, and `stat` (`.claude-plugin/types/claude-code/index.d.ts`, `fs`), none of which fails when its path exists or renames, so two sessions racing in the library could both start a copy. Each session spawns `cmod program <mod> -- <command…>` through `spawnCmod` on `engineOf(mod)`. `cmod program` in `cli/src/commands/program.ts` takes `instances/<mod>/<program>.json.lock` in the cmod store with `takeLock`, whose `rename` of a staged folder is the atomic step, writes the copy's address, pid, and start time to `instances/<mod>/<program>.json`, and every waiting `cmod program` prints each address that file holds, so each stdout line the job reads is the address of the copy that runs now. Bun 1.2.21 keeps `process.ppid` from the process's start, so the holder notices its session died by checking that the parent's pid still runs with the same start time.
- Claude Code 2.1.305 sets no `CLAUDE_CODE_EXECPATH` for a `$.process.spawn` child, and its PATH can lack `claude`, so `claudeCode` in `cli/src/claude.ts` runs the first that exists of `CLAUDE_CODE_EXECPATH` and the Claude Code that is the program's parent process, else `claude` on PATH, because Claude Code's updater deletes the version a running session started from.
- Claude Code tells a forked session nothing about the session it came from. `/branch` forks inside the running process, and `--fork-session` and a move to the agents view start a new process on the fork's id with the copied conversation, which the cmod plugin matches to its parent.
- Claude Code 2.1.295 and later write a plugin's `.claude-plugin/types/` under `claude -p` only when `CLAUDE_CODE_PLUGIN_DIR_WATCH=1` is set.
