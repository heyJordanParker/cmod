# Claude Mod Manager

Claude Mod Manager (cmod) installs Claude Code mods, runs their install and uninstall steps with the person's consent, and builds and publishes new mods.

# Facts

- No Bun workspaces: a workspace hoists packages to the root `node_modules`, outside a plugin's import boundary.
- `core/` publishes as `@cmodjs/core` on npm, the library mods import.
- `cli/` publishes as `@cmodjs/cli` on npm, which ships only the launcher in `cli/bin/cmod`. `cli/src/` is the cmod program's source, compiled into the binaries each GitHub release carries.
- The cmod program is the one runner of a mod's steps, and the library never runs them.
- The cmod program in `cli/` imports the `src/` modules of `@cmodjs/core` as a dev dependency. The library never imports the cmod program.
- `.claude-plugin/plugin.json`, `core/package.json`, and `cli/package.json` share one version, which is the version of the cmod program too. `coreVersion` in `core/src/records.ts` holds it as well, because a published mod bundles `@cmodjs/core` and ships no `node_modules` to read it from.
- Raising that version in all three files, with the root `package.json`'s `@cmodjs/cli` and `@cmodjs/core` ranges, and pushing to `main` releases both npm packages and the cmod plugin. CONTRIBUTING.md has the release steps.
- `core/docs/` ships inside `@cmodjs/core` as the mod author docs, so a change to the Public API changes `core/docs/` in the same commit.
- The sample mods `file-tree` and `architecture-diagrams` are checked out beside this repository.
- A plugin's `cmod.call` hook answers `{ value }` or `{ deny }`. Claude Code 2.1.296 resolves the caller's `$.cmod.call` with the bare value, and rejects it with `<caller>: $.cmod.call: <deny>`. `calledAnswer` in `core/src/testing/fake-claude.ts` makes the test kit answer the same way, and `withBareRefusals` in `core/src/runtime/dependencies.ts` strips that prefix before a mod sees the error.
- Every failure cmod catches for a mod shows through `showFailure` in `core/src/runtime/toaster.ts`: an error toast that stays, with a Copy button for the whole error.
- Claude Code runs `session.start` down the chain of plugins, and `startMod` in `core/src/register.ts` starts its mod while it passes `session.start` on, so every mod starts at once, whatever its place in the chain. A `cmod.call` to a mod that is still starting waits for its start, and one to a mod waiting on its install is refused with "is installing".
- `sessions` and `settings.<source>.update` reach the cmod plugin through `cmod.call`, and it answers by running `cmod history` and `cmod settings`. The conversation index is `history-8.sqlite` in the cmod store. It holds where each message is in its transcript, never a copy, plus each session's turns, contexts, and tasks, and a change to what it holds or how it reads a transcript raises the number in the file's name, so a newer cmod deletes the older file instead of migrating it.
- The cmod plugin is the one reader of the running conversation: `registerMod` adds `session.append`, `session.receive`, `agent.spawn`, and `prompt.attachment` handlers only for it, and the cmod plugin's own `session.compact` route reads each compaction, `core/src/session/conversation.ts` turns each row into messages, turns, contexts, and tasks, and the plugin pushes each change to the mods that listen through `cmod.call`. Other running sessions reach it through one `cmod history follow` child, woken by `fs.watch`. It indexes at session start only while a mod other than cmod holds the `conversation` grant.
- The cmod plugin owns every `before` point of its session, in `core/src/runtime/before.ts`, because only it hears `session.append`, `session.receive`, `agent.spawn`, and `prompt.attachment`, and only its `session.compact` route reads each compaction. It asks a mod of its own session by `cmod.call` and a mod of another session over the relay. `testMod` installs the same points in front of the tested mod.
- Every `Session` action and every `before` on another running session travels as a `<cmod-relay>` message the cmod plugin sends with `$.session.send` and the other session's cmod plugin consumes in `session.receive`, in `core/src/runtime/conversations.ts`. A mod's `before` registrations are a file per session under the cmod plugin's data folder, `before/<session>.json`, which each cmod plugin reads at its start and on a relayed `watch`.
- Claude Code's `TaskCreate`, `TaskUpdate`, and `TaskList` tools and its `TaskCreated` and `TaskCompleted` hooks are its todo checklist. A cmod `Task` is work handed to another session, whose `owner` is that session, and Claude Code's checklist is not part of the model. A mod hears the two hooks as `sessions.current.onTodoCreate` and `onTodoComplete`, with a `before` method for each.
- A mod's `rules/` folder reaches Claude Code as a symbolic link in Claude Code's rules folder, which `syncRules` in `cli/src/rules.ts` places and removes from the settings files and the consent file. cmod records each link it places, and each `claudeMdExcludes` entry it adds to keep a user-wide mod's rules out of a project that turned the mod off, in `rules.json` in the cmod store, and undoes only those, so a link or setting a person made is never touched. Claude Code 2.1.296 loads a linked subfolder, a rule without `paths` only at a session's start, and a rule with `paths` at the first matching read, so the cmod plugin adds a rule without `paths` to a running session as a note.
- Claude Code refuses a hooks module whose `addHook` event name is not a string literal at the call site, so `registerMod` in `core/src/register.ts` names each event literally, and a test in `core/tests/register.test.ts` checks it does and that every hook a session method hears is registered.
- Claude Code refuses a hooks module that holds `import()`, so no file a hook loads uses one. `ui/markdown.js` holds the markdown block kinds and the markdown reader, so only a mod that imports it pays the 18 ms its parser takes to load. A test in `core/tests/register.test.ts` fails on any `import(` in a `core/src` file outside the test kit.
- Anthropic's plugin directory fails a bundle that holds a hook able to answer allow to a permission, and a bundle that declares a second `register`. So `core/src/runtime/permission-check.ts`, the one module that hears Claude Code's permission check for `onPermissionCheck`, `beforePermissionCheck`, `onPermissionRequest`, and `beforePermissionRequest`, is used only by `registerPermissionCheck` in `core/src/register.ts` and by the test kit, so the bundler leaves it out of a mod that never calls `registerPermissionCheck`. Its allow and ask answers sit in an `if (!globalThis.cmodWithoutApprove)` block, which `bundledHooks` in `cli/src/commands/publish.ts` defines as `true` through `bundleDefines` in `core/src/records.ts` for a mod without `"approve": true`, so Bun drops the block and the bundle of a mod that only refuses holds no allow. Bun drops an `if (false)` block without minification, and syntax minification reshapes `addHook` calls past what `claude plugin validate` accepts. A test in `core/tests/register.test.ts` bundles a mod each way to check it.
- Claude Code 2.1.302's `HookBudget` type says a hook's 10 s budget stops while any `$` call of the hook is in flight, `$.cmod.call` included and a `$.clock` wait excepted, so a listener's `deadline` is the end of its `timeoutMs` and no earlier. The engine event `session.end`, which `registerMod` does not register, runs its whole chain under one wall-clock bound instead.
- Claude Code 2.1.302 raises `classic.SessionStart` with source `compact` for a subagent's compaction too, with no `agent_id`, and puts its note in that subagent's window. Only `session.compact`'s `agentId` names the agent. So no listener hears SessionStart's compact, and `compactionNote` in `core/src/runtime/sessions.ts` answers `beforeSessionStart` from the resolved `session.compact`, which `registerMod` registers for every mod: its note as a message added to the new window, and its title, Skill reload, and first prompt at the next SessionStart(compact), because Claude Code 2.1.302's SessionStart handler keeps those for the whole session, whichever agent's SessionStart carries them.
- Every note a mod gives travels inside its tag, `<{mod}_mod>…</{mod}_mod>`, from `modNote` in `core/src/session/context/turn/message/note.ts`, and `unplacedOf` in `message.ts` turns each tagged block of a `hook_additional_context` row, or a user message that holds only tagged blocks, into a `Note` from that mod. Claude Code's hook row names no plugin, so the tag is the only way to tell whose note it is.
- Claude Code skips a hook that throws or runs past its budget, as if the plugin had none, unless the registration carries a `.catch`, and `claude plugin validate` notes each gating hook without one. So every hook `registerMod` adds after `session.start` carries one, `lifecycle.caught` in `core/src/runtime/lifecycle.ts`, which answers with the failure answer a route gave `router.add` beside its hook, so each gate refuses in its own answer's shape.
- Every `Mod` member is the mod's own. What is Claude Code's or the computer's is an import from `mod.js`: `sessions`, `settings`, `model`, `fs`, `metadata`, `process`, and `http`, each bound to the mod that runs it. Built-in jobs reach Claude Code's hooks API through `engineOf(mod)` in `core/src/runtime/engine.ts`, which no mod-facing doc names.
- A mod's `CHANGELOG.md`, in the Keep a Changelog format, is its release notes. `core/src/utils/changelog.ts` reads it for `cmod publish`, the Updated toast in `core/src/runtime/announce.ts`, and the Changelog section of each mod in Settings. cmod's own root `CHANGELOG.md` gets the version's section before each release, because the release workflow runs `cmod publish`, which refuses a version without one.
- The cmod plugin draws every mod's widgets, because one row holds widgets of several mods and one plugin lays the row out, and Claude Code 2.1.302's `$.ui.invalidate('ui.render')` redraws only the calling plugin's renders. `serveWidgets` in `core/src/runtime/widgets.ts` keeps the layout in `widgets.json` in the cmod store and draws each area in a component Claude Code already renders: `AbovePrompt` in `AbovePrompt`, `BelowPrompt` in `PromptHint`, `Working` in `Spinner`, `TurnEnd` in `TurnDuration`, and `Dashboard` in the Sidebar's Dashboard tab. A mod tells the cmod plugin its widgets and pages through `cmod.call` on each change and every time it starts, even with none, and draws each as data, `elementData` in `core/src/ui/elements.ts`, because an element and a closure cannot cross plugins. A press travels back by `cmod.call` with the handler's number. Claude Code 2.1.302 skips a plugin's `cmod.call` hook when the call comes from code running inside that plugin's own call, as `skipped: re-entry` in the debug log, so `createUi` in `core/src/runtime/ui.ts` runs a pressed handler inside the press call and `collect`s the updates it would send, which return in the press's answer. A `TurnDuration` render's `requestId` is the uuid of the `turn_duration` row, which `turnClosedBy` in `core/src/runtime/conversations.ts` maps to its turn.
- Each `cmod` command that changes the set of mods writes `plugins-changed`, whatever its exit code, because a command can change some mods before it fails, in the cmod store, from `markPluginsChanged` in `cli/src/store.ts`, called by `cli/src/main.ts`. The cmod plugin watches the file, Claude Code's `installed_plugins.json`, and the user `settings.json`'s `enabledPlugins` with `fs.onChange`, so a change from `/plugin`, `claude plugin`, or Claude Code's automatic update reloads too, and runs `/reload-plugins` through `$.command.run` from a `mod.after` timer. Claude Code 2.1.305 keeps the prompt cache across that reload when the change is a plugin's commands, skills, agents, or hooks: a live run read the whole conversation from the cache on the next turn. It runs it from a timer because Claude Code 2.1.302 refuses `$.command.run` inside a `command.run` hook. It reloads once per new mark, folds a burst into one reload, reads the mark again after each reload so a mark written during one is not lost, and never reloads for the mark it started with.
- The cmod plugin draws the Sidebar, one pane holding the Dashboard, the pages mods open, and Settings, in `src/sidebar.ts` and `src/settings.ts`, and applies each mod's page requests through `servePages` in `core/src/runtime/pages.ts`. Claude Code 2.1.303 places a `$.ui.open` at any width only inside the hook of the person's own input, so `createUi` marks a request sent inside a `command.run` or `ui.press` hook `isAsked`, and the cmod plugin opens the Sidebar for each asked request in that same frame: after `next(e)` when it comes first in the chain, and on a mod's `next(e)` when it comes later. Claude Code 2.1.305 runs the chain in an order a mod cannot choose, such as `notes@cmod, cmod@cmod`. A request from a timer or a listener is unasked, and Claude Code places it only at 144 columns or wider.
- A hotkey is a hidden immediate command `<mod>--<hotkey>` the mod registers, hidden through `command.describe`, and bound in Claude Code's `keybindings.json` as `command:<mod>--<hotkey>`. `keybindings.json` is the one source of each hotkey's combo: `boundCombos` in `core/src/records.ts` reads it for the mod, `cmod setup` binds the declared defaults and keeps a combo the person rebound, and `cmod hotkey` in `cli/src/commands/hotkey.ts` rebinds one. The cmod plugin has no install record, because `setup/bootstrap.sh` installs it, so it binds its own two hotkeys once through `cmod hotkey`, guarded by its `areHotkeysBound` global state.
- A command a plugin registers runs through `command.run` and then, when the last hook calls `next(e)`, through Claude Code's own run of it, which answers `<plugin> registered /<command> but no command.run hook answered it` whenever the hooks gave no `text`. Claude Code 2.1.305 shows any `text` as `<plugins>: <text>` under the typed or key-bound command, and shows no row for `{}` from a hook that did not call `next(e)`. So `answerInput` in `core/src/runtime/ui.ts` runs a hotkey or a `slashCommand` reply and calls `next(e)` only when the cmod plugin answered one of its page requests with `isHeld: false`, because the cmod plugin comes later in the chain. The cmod plugin's `command.run` route in `core/src/runtime/pages.ts` then opens the waiting requests in that frame and answers `{}` without calling `next(e)`, so Claude Code's own run never happens. The test kit's `type` and `hotkey` reject a command that reaches Claude Code's own run with no `text`.
- `fs.onChange` checks its paths every 500 ms from a `claude.clock.every` timer, in `core/src/runtime/watches.ts`, and stops a call over 2000 files with an error toast, instead of Claude Code's SessionStart `watchPaths`, which a mod loaded mid-session never answers and another mod's answer replaces.
- A message that needs the person to act carries its fix as one of three sentences in `core/src/records.ts`, `grantFix`, `installFix`, and `secretFix`, because a refusal crosses plugins as a bare string. `createToaster` in `core/src/runtime/toaster.ts` adds the `Settings`, `Plugins`, or `Open /config` button to a failure toast whose text holds one.
- Claude Code gives a mod that loads mid-session `session.start` and no `classic.SessionStart`. So `createLifecycle` replays SessionStart with source `resume` before the first `classic.UserPromptSubmit` of a mod that heard none.
- A mod's dependency on a bare `cmod` resolves in the declaring plugin's own marketplace, and only an inline plugin, from `--plugin-dir` or `CLAUDE_CODE_PLUGIN_DIRS`, leaves it unqualified so any enabled cmod satisfies it. `{ "name": "cmod", "marketplace": "cmod" }` resolves to cmod@cmod, and Claude Code 2.1.303 installs that only when the person already added the `cmod` marketplace. So `cmod link` keeps `CLAUDE_CODE_PLUGIN_DIRS`, which Claude Code reads only when a session starts.
- Every newer cmod runs every mod built on `@cmodjs/core` 4.0.0 or later, so a mod's `cmod` dependency is `>=` the `@cmodjs/core` it bundles, which `cmod check` writes and `cmod publish` requires. So the `--events` lines, the `cmod.call` methods in both directions, the relay kinds and actions, `widgets.json`, and the consent hash keep their 4.0.0 shape: a newer cmod adds a line type, a method, a kind, an action, or a field, and never changes or removes one. `core/tests/contract.test.ts` freezes the event lines, the consent hash, and the methods a mod answers, the contract test in `tests/mod.test.ts` the methods the cmod plugin answers, and `core/tests/runtime/conversations.test.ts` and `core/tests/runtime/widgets.test.tsx` the relay kinds and `widgets.json`. A relay receiver refuses a kind or action it lacks by name, and the `widgets.json` writer keeps the areas, row fields, and placed widgets it does not know.
- Claude Code 2.1.305 loads one plugin named `cmod` when several marketplaces list one, the first source whatever its version, and checks each mod's range only against its own marketplace's copy. So the cmod plugin runs `cmod update cmod` when Claude Code's `installed_plugins.json` changes and `cmod list --json` shows a mod off for an older cmod or two copies at different versions, and a mod whose cmod program stays older than its `@cmodjs/core` for a minute runs it too.
- The library runs the cmod program only as `<store>/programs/cmod`, never a `cmod` on PATH, and reads its version from the newest folder of `<store>/bin/cmod`, the one the launcher runs, without starting it.
- Claude Code 2.1.305 sets no `CLAUDE_CODE_EXECPATH` for a `$.process.spawn` child, and its PATH can lack `claude`, so `claudeCode` in `cli/src/claude.ts` runs the first that exists of `CLAUDE_CODE_EXECPATH` and the Claude Code that is the program's parent process, else `claude` on PATH, because Claude Code's updater deletes the version a running session started from.
- Claude Code tells a forked session nothing about the session it came from. `/branch` forks inside the running process, and `--fork-session` and a move to the agents view start a new process on the fork's id with the copied conversation, which the cmod plugin matches to its parent.
- Claude Code 2.1.295 and later write a plugin's `.claude-plugin/types/` under `claude -p` only when `CLAUDE_CODE_PLUGIN_DIR_WATCH=1` is set.
- `site/` is claudemodmanager.com, a VitePress site GitHub Pages serves. Its landing page is `site/index.md`, and its docs are `core/docs/` of the latest release tag, copied in at build. `bun run --cwd site dev` serves it locally with the working tree's `core/docs/`.
- `site/mods.json` is the list the site's Mods page shows, and a pull request adds a mod to it.
- The site's build writes `llms.txt`, `llms-full.txt`, and a Markdown copy of each docs page, and `site/public/og.png` is the image a shared link shows.
